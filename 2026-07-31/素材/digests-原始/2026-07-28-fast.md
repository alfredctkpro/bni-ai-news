## 🟢 工具用法

### 🔥 熱點卡 1 · Opus 5 發布：同價、逼近 Fable 5、抗 prompt injection 最強（🔥 8 人在談）⚠️⚡
- **一句話**：Anthropic 發 Claude Opus 5，API 價格與 Opus 4.8 完全相同（$5/$25 per M token）＝**Fable 5 的一半價**，多項評測超過 Fable 5；Boris Cherny 強調重點不是跑分而是「**史上最不易被 prompt injection 的模型**」。
- 🏢 **ctkpro**：這是**成本結構直接變動**——原本要用 Fable 5 才敢跑的長任務（大重構、跨檔案改造），現在可用一半價跑。Claude Max 訂閱的性價比重新成立（歸藏原話：不出這個「Max 都沒必要續訂了」）。**抗注入變強**對「agent 接客戶系統／讀外部內容」的案子是護城河等級的安全訊號，P1 部署流程裡讓 agent 讀外部 issue／網頁的環節風險下降。
- 🧠 **me**：本週該做的是**重跑一次自己的主力工作流基準**（Vibe Coding 大精進的實測素材），確認「Opus 5 是否可取代 Fable 5 當日常主力」。
- 多方觀點：@bcherny 官方強調「least prompt injectable」非跑分｜@alexalbert__ 主打 token 效率＋「產出接近顧問水準的簡報/試算表」｜@op7418 實用派叫好但抓包官方圖表標紅標錯（53.4>53.5）｜@steipete 轉 @cheaty 警告：**踩到 guardrail 會無聲 fallback 回 Opus 4.8，不通知**（實務要注意）｜Simon Willison 尚未實測、只轉發

### 🔥 熱點卡 2 · Anthropic 砍掉 80% 系統提示詞、編程分數不掉 → 「刪比加更有效」（🔥 4 人在談）⚡🔗
- **一句話**：Thariq（Claude Code 團隊）公開：新模型上，他們**移除約 80% 的 Claude Code 系統提示詞，編程評測毫無損失**；官方另出 Opus 5 提示指南，主軸就是「教你刪東西，而不是加東西」。核心論點＝提示詞只是模型取得上下文的一小部分，模型越強，硬塞的規則越變成雜訊。
- 🏢 **ctkpro**：**直接可執行的健檢**——公司導入 VS Code/GitHub 那套（P4 團隊工作方式系統化）累積的 `CLAUDE.md`／規則檔／Skills 很可能已經過度膨脹。該排一次「規則瘦身」：刪掉模型現在已內建的常識性規則，只留「我們公司特有的、模型猜不到的」。這同時降低每次呼叫的 token 成本。
- 🧠 **me**：對照我自己的 thinkr CLAUDE.md／agent 定義——**「寫更多規則」的直覺是錯的**，該練的是判斷「哪些規則是模型已經會的」。
- 🔗 建議 /ingest：這條可升級成模型——「規則瘦身／上下文減法」，與 [認知負荷理論](../../../4_kb/thinking-models/學習教育/認知負荷理論.md)、[外部大腦與知識凝縮](../../../4_kb/thinking-models/學習教育/外部大腦與知識凝縮.md) 同族（外部化知識不是越多越好，過量反成噪音）。
- 多方觀點：@Thariq/@bcherny 官方數據｜@op7418 導讀「隨模型提升該如何更新自己的上下文規則」｜@xiaohu 整理官方 Opus 5 提示指南中譯

### 🔥 熱點卡 3 · 語音成為 agent 的新介面：Codex/ChatGPT 桌面版接 GPT Live（🔥 5 人在談）⚡
- **一句話**：ChatGPT 桌面端（原 Codex App）加入即時語音控制，可**純語音指揮 agent 寫程式、操控電腦、調度 ChatGPT Work**；配 AirPods 可離開鍵盤在家任何地方交互。另有人指出「ChatGPT Voice 是我用過最好的 plan mode」——用嘴談需求、AI 反問把模糊想法問清楚。
- 🏢 **ctkpro**：這對「**下午 3 點後腦力下降**」的現實是實質解——把耗腦的鍵盤輸出換成低負荷的口說對談。P4 交辦同事時，語音 plan mode 也降低「不會寫 prompt」的入門門檻（比教打字下指令好教）。
- 🧠 **me**：值得本週試——**用語音跑 plan 階段、鍵盤跑執行階段**的分工，正好搭 Typeless 已在用的口說習慣。

### 🔥 熱點卡 4 · 「AI 寫的程式碼要不要逐行看」：Bob 大叔說不看，宝玉說先寫測試（🔥 3 人在談）⚡
- **一句話**：《Clean Code》作者 Bob 大叔表態「**我不看 AI 寫的程式碼**」——人類讀碼太慢，逐行審查就失去用 AI 的意義；但不看≠不管，他改成給 AI 設好約束與驗收。宝玉補上工程紀律版：AI 讓重構成本降低，但**做事方式沒變——重構前先寫好測試（哪怕測試是 AI 寫的）**，因為 AI 真正擅長的是「出錯後反覆自我糾錯」，所以測試覆蓋率對 AI 特別重要。
- 🏢 **ctkpro**：這是**可直接落成團隊 SOP 的一條**——把 code review 的位置從「逐行看 diff」移到「看測試與驗收條件」。呼應 P4「團隊工作方式系統化」：同事用 agent 產碼時，該檢查的是測試是否先於實作、而非讀完每一行。
- 🧠 **me**：對「架構師之問」的具體化——我的角色是設計驗收機制，不是當人肉 linter。
- ⚠️ 反面提醒：宝玉同串指出**AI 寫的爛測試是負資產**（兩個原因：需求上下文沒理解對／早期模型能力不足），所以測試本身仍要人審。
- 🔗 [Bob 大叔：我不看 AI 寫的碼](https://x.com/dotey/status/2080460993251951103)｜[宝玉 · 重構前先寫測試](https://x.com/dotey/status/2080394768908013629)｜[AI 測試可能是負資產](https://x.com/dotey/status/2080397267199283439)
