# YouTube Digest · 2026-10-09

> **本期一句話：上週的結論是「驗收要放在 agent 外面」，這週 AI Engineer NYC 的幾場演講補上下一步：負責驗收的那個東西也得有人驗。** Browserbase 和微軟拿人工標記去比對，業界常用的 LLM 評審說某個 agent 成功率 74%，實際只有 38%。他們的說法是：「你以為在訓練更好的 agent，其實是在訓練一個更有自信的騙子。」Amazon 的經驗是，可靠度 80% 時客戶仍然不信任（他們還得盯著、還得補做），要到 90% 才會把整段工作交出去。成本這邊也是同一件事：OpenAI 在 DevDay 自己說，要看「每件任務的成本」，**而且要把人接手的時間算進去**。Haiku 5.5 和 Luna 的每 token 價格一樣，實測每件卻差 7 倍。

## 🟡 前沿翻盤

### ⚡⚠️🔁 熱點卡① · Haiku 5.5、Luna、Sonnet、Opus：單價一樣，每件差 7 倍；OpenAI 自己說要算「每件成本＋人接手的時間」
🔥 **約 9 個頻道在談**（Chase AI ×2、Nick Saraev、WorldofAI、Nate Herk〈Opus 5.5 vs Sonnet 5.5〉、OpenAI〈Stop Overpaying for Intelligence〉、IndyDevDan、AIDB〈The Best Way To Test New AI Models〉、Futurepedia）

- **深判四支就夠**：[Chase AI〈Haiku 5.5 vs Luna〉](https://www.youtube.com/watch?v=JJMChiMYW_g)（價格懸崖）、[Nick Saraev〈花 700 美元測 Haiku／Sonnet／Opus〉](https://www.youtube.com/watch?v=DMQEPzSxGVk)（品質落差比價差小）、[OpenAI〈Stop Overpaying for Intelligence〉](https://www.youtube.com/watch?v=_nmlHbSB8kM)（官方的成本方法）、[AIDB〈The Best Way To Test New AI Models〉](https://www.youtube.com/watch?v=HX8Zr1kmLEQ)（自建評測的五個步驟）。WorldofAI〈90% CHEAPER〉未轉錄，看標題是複述跑分，不必看。
- **Haiku 5.5 的價格（Nick Saraev）**：每百萬 token 輸入 0.10、輸出 0.50 美元（Haiku 4.5 是 1／5 美元），快取讀取再打一折；**超過 10 萬 token 之後變成 0.50／2.50**。他的實測：同一份鑑識會計題（從大量 CSV 找出 8 筆舞弊），**Haiku、Sonnet、Opus 都是 8／8**；做 Minecraft 風格的方塊遊戲，Haiku 花 0.20 美元；高級手錶的形象網站，Opus 最好，但 Haiku 的成本只是它的零頭（他口述的倍數聽不清，不引數字）。他的結論：「**Opus 的品質沒有比 Haiku 好 40 倍，差距比價差小很多。**」分工建議：**Opus 規劃，Haiku 動手**，例如摘要報告、工單分類、查資料庫、從一萬筆數字裡找出一筆。
- **🔧 但每件成本要實際跑才知道（Chase AI，Haiku 對 Luna，同一個 harness）**：
  - 官方跑分 Haiku 全面贏，Artificial Analysis 的指數也是 Haiku 43 分、Luna 38 分。但**拿到 43 分每件要 0.21 美元，38 分只要 0.07 美元**；那次 50 個步驟裡，有 31 步是按 5 倍單價計費。
  - 他的實測：同一個訂房網站，low 檔 Haiku 0.036 美元、Luna 0.01 美元；**max 檔 Haiku 1.25 美元、跑了 27 分鐘，還失敗一次要重來；Luna 0.046 美元、9 分鐘**。滑雪小遊戲 Haiku 在 extra-high 檔**因為輸出超過約 12.8 萬 token 的上限，反覆卡死，什麼都沒交出來**。總計：**Luna 便宜將近 7 倍、快 37%，而且每一題都做完了**。
  - Haiku 唯一大勝的是長文件檢索（8-needle）：**96% 對 29%**。所以他的分工是：**簡單、量大、在意成本的用 Luna；長文件、要求準確的用 Haiku，effort 不要開太高**。
- **OpenAI 官方的成本方法（DevDay 分享）**：
  - **看 cost per task，不看 cost per token**。例子是航空公司的客服機器人聽不懂改票需求，最後要求轉真人：「每件成本是 token 加上那位客服的時間。」
  - **畫準確率對成本的 Pareto 曲線**：先定這個任務要達到的準確率門檻（例如 80% 的詢問由機器人結案），再找出達到門檻的最便宜組合（模型、設定、harness）。
  - **模型以外的四個槓桿**：①**提示詞快取**，最多省 90%，把固定的開頭放在前面（Blitz 的快取重用率從 24% 提到 90%）②**programmatic tool calling**：讓模型寫一小段程式去串工具、整理結果，不要把所有中間資料都塞回給模型（Clio 少了 38% 的 prompt token，品質沒有下降）③**effort 從低開始**，用 eval 確認品質撐得住再往上加 ④不急的工作用 batch，**便宜 50%**。
- **自建評測的方法（AIDB × Nufar Gaspar，可以直接當 Vibe P5 的流程）**：①挑 **4～6 個**真的會用到的任務，要涵蓋不同類型，**優先挑「做壞了一眼就看得出來」的任務**，**另外放一題「目前 AI 做不好、但希望它能做」的願望題** ②候選最多 4 個，**一定要包含你現在用的組合當基準** ③每題開新對話，**把模型名稱藏起來**，自己打 1～5 分並寫一句評語 ④若要用 AI 當評審，**挑另一家的模型**（同一家的模型會偏袒自家），而且要**先確認評審的判斷和你一致**。她的評審和她本人只有一題意見相同，評審只看得到程式碼、看不到網站畫面 ⑤決定只有三種：**換、分用、不換**。訂閱方案的補貼會掩蓋真實成本，「之後未必還會這麼大方」。
- **🏢**：①**報價和 Vibe P5 的分母定案**：每件成本＝**通過驗收的 token 成本＋人接手的時間**；量測表加兩欄：**人工介入分鐘數**、**單件 token 長度**（Haiku 跨過 10 萬就是 5 倍單價）②**ctkpro 的客服、文件類專案**，可以把 OpenAI 那四個槓桿寫進技術方案，尤其是「固定開頭放前面」和「程式碼串工具」，這兩項幾乎不用改架構。
- **🧠**：Vibe P5 對照組加入 **Haiku 5.5 和 Luna**（effort 都用 medium），流程照 AIDB 的五步；**願望題可以放「寫週報」或「從 journal 整理本週決策」**，這類任務目前都還要你來回修改好幾輪。
- ⚡⚠️🔗（可掛 [邊際分析](../../../4_kb/thinking-models/複雜性/邊際分析.md)：多花 3 倍成本換 5 分；[古德哈特定律](../../../4_kb/thinking-models/領導力/古德哈特定律.md)：只看每 token 價格）
- ⏱ **OpenAI 那支 22 分鐘，前 12 分鐘必看**（cost per task 和四個槓桿），講法比任何第三方都權威，可以直接引用在客戶提案。**Chase AI 看前 5 分鐘的價格懸崖和最後 3 分鐘的總結**。AIDB 那支 50 分鐘，看第 3～25 分鐘的五個步驟就好。Nick Saraev 是遊戲 demo，**只看最後 4 分鐘的價格和分工**。

## 🔵 Agent 範式

### ⚠️🏛️🔁 熱點卡② · 驗收者也要被驗收：LLM 評審說 74%、真值 38%；可靠度 80% 客戶不信、90% 才交棒
🔥 **AI Engineer 7 場演講 ＋ OpenAI DevDay 1 場**（Browserbase〈Your LLM Judge Is a Confident Liar〉、Amazon AGI Lab〈Why 80% Reliability Isn't Good Enough〉、Meticulous〈Why AI Didn't Actually Make You Ship Faster〉、Sonar〈AI Writes More PRs. Who Validates Them?〉、Datadog〈Your LLM App Returned 200 OK. It Was Still Wrong.〉、Arize〈From Vibes to Production 101／201〉、Braintrust〈Why Building an Eval Platform Is Harder Than It Looks〉；DevDay〈Qodo - The Last Human Code Review〉）

- **Browserbase × 微軟〈Your LLM Judge Is a Confident Liar〉（本卡主幹）**：
  - **數字**：同一個網頁 agent，WebVoyager 官方評審（GPT-4o）說成功率 74%，用他們重做、和人工標記高度一致的評審去量，**只有 38%**。「拿這種評審當 RL 獎勵，**你不是在訓練更好的 agent，而是在訓練一個更有自信的騙子**。」
  - **舊評審的毛病**：用比較弱的模型、沒有評分細則、不看相關截圖（或者全看，結果塞爆 context）、**沒看最後的答案和動作紀錄**。
  - **新評審的四條原則**：①**只評任務要求的東西**，不另外加標準（不然分數會被不公平地拉低）②**前一步的錯不要連帶扣到下一步** ③**一定要看實際狀態（截圖），不能只聽 agent 說它做了什麼**，「agent 常常很有自信地說做了，其實沒做」④**分開 agent 能控制和不能控制的失敗**（商品缺貨，agent 盡力了，過程給滿分，但結果仍算沒達成）。
  - **怎麼證明評審可信**：誤判為成功的比例從將近一半降到接近零；它和人工標記的一致程度（Cohen's kappa 0.58），**跟兩個人類標記員彼此之間一樣**。**三分之二的人工標記在建構時完全沒看過**，避免過度擬合。
  - **AI 能不能自己做出評審**：他們花三週、跑 30 次實驗做出來；auto-research 一天就跑完同樣多的實驗，**但一致程度只有他們的 70%**。把他們三週的發現餵給它之後，結果比他們自己做的還好。→「**人的直覺加上自動迴圈**」是目前最好的配方。
- **Amazon AGI Lab（Nova Act）〈Why 80% Reliability Isn't Good Enough〉**：
  - **信任懸崖**：「你說 80% 可靠，客戶聽到的是：我還得盯著它、失敗了還得自己補，**這反而是更多工作**。到 90% 左右，訊息才變成：我可以把整段流程交給它。」**可靠度對客戶來說是 0 或 1**。
  - **誠實講清楚範圍，比更高的跑分更能建立信任**：要講三件事，做得好的、正在改進的、**不在範圍內的**。「不然他們試一次失敗，就換下一個工具了。」
  - **eval 情境要從正式環境來，不能靠想像**；每週都該變得更聰明，「沒變，就代表你的 eval 過期了」。案例：替 Amazon Leo 加了「**軌跡快取**」，同樣的流程直接重播、失敗才叫模型，用來降成本。
- **Meticulous**：「斷言式測試永遠寫不完所有可能的退化。」做法是錄下真實使用者的操作流程，每個 PR 重播一次、每一步截圖、前後比對，**它不告訴你有沒有 bug，只把差異擺出來，由人（或 agent）判斷是不是預期中的改變**。
- **Sonar（收購 Gitar）**：客戶授權 agent 的順序很固定：**先只看審查意見 → 讓它可以擋 PR → 讓它自動修 → 最後才依規則自動核准合併**，每一級都是因為上一級累積了信任。（產品介紹，但這個順序可以借用）
- **Qodo（DevDay）**：①最低限度的指標：「**完成一個高品質 PR，開發者被叫了幾次**」，也就是不再是人去 prompt agent，而是 agent 來 prompt 人 ②coding agent 和審查 agent 意見不同時，才交給人決定 ③**「wisdom base」**：掃過去幾年 PR、Slack 上的討論，把資深工程師腦中的部落知識整理出來，餵給審查（他們的客戶是東南亞一家大型金融機構，有些資深工程師已經離職）④「**任務的單位不該是 PR，是一個完整功能的整包工作**」。
- **🏢**：①**交付規範要加一條「驗收者驗證」**：凡是用 LLM 當評審或審查的地方，**先準備 30～50 筆人工標記的樣本，量評審和人的一致程度**，過了才上線，這可以寫成 ctkpro 的標準工序 ②**對客戶的承諾用 Amazon 的三段式說清楚**：做得好的、正在改進的、不做的。這和 P2 的「承諾尺度書面化」是同一件事 ③**授權順序照 Sonar 的四級**，寫進導入提案：看 → 擋 → 修 → 合併。
- **🧠**：**10/5 Retro 的「打槍率」要多一層**：誰判定被打槍？如果是用 AI 判的，先抽 20 筆自己看，確認 AI 的判斷和你一致。Qodo 的「人被叫了幾次」可以當打槍率的反面指標。**你的 digest 本身就是一個 LLM 評審**（_judge.md），這張卡等於提醒：偶爾要抽幾則被砍掉的料回頭看。

### ⚠️🏛️🔁 熱點卡④ · 權限與資安的具體做法：沙箱裡零憑證、按意圖切沙箱、滲透測試改成每個 PR 都跑
🔥 **6 場演講**（Docker〈How Many Credentials Should Your AI Agent Have? Zero.〉、Docker〈YOLO Mode, Safely: MicroVM Sandboxes〉、E2B〈Love the Sandbox〉、Google DeepMind〈Why AI Agents Should Have Their Own Sandbox〉、Snyk〈AI Hackers Are Faster Than Your Pen Test〉；YAHA〈Task budgets〉。後三場只看標題，未轉錄的不臆測）

- **Docker 的 Jim Clark（本卡主幹）**：
  - **「一個沙箱裡該有幾把憑證？永遠是零。」** 憑證放在沙箱外的 MCP gateway，所有工具呼叫都經過它，它就是控制點；**換 Claude Code 或 Codex，工具設定都不用重做**。
  - **按意圖切沙箱（新聞編輯室的比喻）**：①研究員可以盡量上網，但沒有任何發佈或寫入的工具，結果只寫到自己的暫存區 ②事實查核**沒有網路**，只能讀研究結果和公司的事實資料庫 ③撰稿兼發佈的那個有發佈用的 MCP，**也沒有網路**。整個流程什麼都碰得到，**但每一步都不會同時擁有「讀進沒過濾的內容」和「能對外動作」兩種能力**。
  - **commit 簽章金鑰的例子**：一小時的任務裡只有大約兩分鐘需要 commit，**金鑰只在那兩分鐘放進沙箱**。
  - **XAA（cross-app access）**：Docker、Anthropic、Okta 一起推的新規格，**用公司現有的 SSO 授權 agent**，不必再一個一個點同意畫面，由公司統一管 agent 能做什麼。
- **Snyk〈AI Hackers Are Faster Than Your Pen Test〉**（產品介紹，數字是 Snyk 自家的）：AI 讓每位開發者多寫 218% 的程式碼；**LLM 產出的程式碼有 62% 不安全或有問題**；43% 的 MCP server 有漏洞；最快的 AI 攻擊 4 分鐘就成功。「一年做兩次滲透測試，剩下的 350 天誰在測？」他們的做法是**每個 PR 都跑一次 AI 滲透測試**。**他給的選商四問很實用**：①是持續跑，還是偶爾跑一次？②有沒有理解應用的商業邏輯（越權存取這類問題，靜態掃描抓不到）？③能吃進多少其他掃描器的結果當 context？④**能不能證明漏洞真的能被利用**，還是只是標出來？
- **YAHA〈別再讓 Claude 偷跑用量！Task budgets〉**：task budget 讓模型知道「這一輪還剩多少 token」，自己決定要繼續查還是開始收尾。但**它只是提示，模型偶爾會超出**；給太少（最低 2 萬）模型可能直接放棄或縮小範圍。建議：**先不設上限，跑一批代表性任務，取第 99 百分位當起點**。最重要的一句：「**模型負責管理工作，你的程式負責執行硬上限。**」
- **🏢（signal 的「結果交給誰」加上本期的「按意圖拆開」）**：①**權限政策範本多一個維度**：每個沙箱「能讀什麼、能對外做什麼、手上有什麼憑證」三欄，**同一欄不能同時有「讀外部內容」和「對外動作」**，這就是 Muse 傳地址、Shane Mac 貼銀行餘額那兩個事故的解法 ②**Q4 的資安盤點**：signal 說掃描已經免費、攻擊測試也有正規管道，ctkpro 能收錢的是授權、範圍和驗收；**Snyk 的選商四問可以改寫成客戶的選型清單**，讓 ctkpro 當選型和驗收的顧問，不必自己做掃描器 ③**Zeabur 善後**：所有按量計費的地方，上限都要寫在程式或平台設定裡，**不要靠模型自己節制**。
- **🧠**：thinkr 的情境（agent 讀 `2_family/`、`0_journal/`，又能 git push、呼叫 Perplexity）正好是 Docker 說的「同一個沙箱同時有兩種能力」。不必現在改，但 Claude Tag demo 可以用「研究和發佈分成兩個沙箱」來示範。
