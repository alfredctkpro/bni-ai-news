## 🟢 工具用法

### 🔥 熱點卡 1 · 「驗證」本週從命題變成出貨的零件 🔥 6 人在談 🔁
- **生成端的成本崩了，帳單轉嫁到測試與審查——而這週工具層第一次給出對應的官方零件。**
  - 🏢 **直接接 Vibe Coding P5 的私有 eval，而且省掉自己造輪子**：`claude plugin eval` 可以建 test case → 跑你的 plugin／skill → 打分 → **再跑一次「不帶 plugin」做對照**，看它到底加了多少價值。官方講明動機就是「新模型發布後，你不知道你的 skill 還能不能用」。搭 yt 那則 Arize 的成本基準（2,300 次呼叫 ×7 模型＝29 美金），**私有 eval 的門檻比想像低**。
  - 🏢 **交付物該多一項**：Boris Cherny 說 Anthropic 內部的護欄是「大量 lint 規則、大量測試、Claude 驅動的 E2E、每日跑的 Claude fuzzer、自動 code review 與安全審查」——**「Claude 寫的 production code 門檻要比人寫的更高」**。這句話可以原封不動放進客戶提案，回答「AI 寫的你敢用嗎」。
  - 🧠 **規模數字幫你算帳**：Anthropic 自曝 Claude 寫 80% 程式碼、工程師每季出貨 8x，**代價是測試 10x、CI job 25x**（他們為此寫了 test impact analysis 才撐住）。→ 這是「cost per finished task」被忽略的另一半：**省下的寫程式時間，會有一部分被 CI 帳單吃回去。**
  - 多方觀點：@ClaudeDevs／@Thariq 出零件｜@Boris Cherny 立標準｜@Addy Osmani 給規模代價｜@Gergely Orosz 唱衰「**code review 名存實亡**，AI 產出多到審不完」｜@宝玉 的段子補刀（同事讓 agent review、作者讓 agent 改、再 review，**人在過程裡主要是複製貼上**）｜**唯一逆風** @Laurie Voss：「寫程式的成本崩了，review、修、維運的成本也在跟著崩……剩下的工作是**搞清楚人真正要什麼、精確定義它、把它做得好用**」

### 🔥 熱點卡 2 · agent 值夜班：第一個「權限邊界」的可運行樣板 🔥 3 則 🔁
- **Anthropic 把 Claude Tag 當 on-call 第一線，重點不在它多會查，在它被允許做到哪一步。**
  - 完整動線（小互轉述官方影片）：晚上 11 點支付介面錯誤率破 2% → 值班工程師還沒開電腦，Claude 已在 Slack 裡查（拉監控、比對最近幾次上線、翻 feature flag 改動）→ **15 分鐘定位**（新功能的重發沒限併發，把佇列衝爆）→ 列兩個修法、推薦一個、**@ 工程師拍板** → 工程師只回「加上限、功能保持開著」，它才動手改 **4 行** → 上線後自己盯 10 分鐘錯誤率，穩住才宣布修好，並留一條給下次的備註「先查 feature flag」。
  - **邊界**：能查問題、能提改碼申請，**但合併與上線必須人批准**。ClaudeDevs 另分享了 CI 團隊的完整設定（讀警報／指標／log → 寫 SITREP → 維護 `lessons.md` 持續學習），附模板與 skills。
  - 🏢 **這正是 slow 圓桌題「可稽核 policy」缺的那個實體樣板**：核准點綁在**具體動作**（合併／上線）、SITREP＝稽核軌跡、lessons.md＝自我改進迴圈。🔁 對照 Mollick 四情境的「Approval」——Mollick 講該在哪停下來問人，**這則示範了怎麼停**。
  - 🏢 **同時是 Q4 漏斗最好賣的 demo 題材**：維運自動化痛點明確、ROI 可算（值班人力／MTTR），而且客戶聽得懂。比「導入 AI」好賣十倍。

### 🔥 熱點卡 3 · 多 agent 工程化：兩份完整清單同週落地 🔥 4 人在談
- **從「換個編碼工具」到「重寫工作方式」，本週同時出現一份原則清單與一整條演講軌。**
  - **Kiro《Frontier Engineering》10 原則**（Clare Liguori 主筆）核心診斷一針見血：**「許多人仍把自己放在 AI 與終端之間，充當人肉路由器、異常傳遞員和點擊確認器。」** 十條：Architect not typist（架構師不是打字員）／**Maximize agent time**（把「60 秒等待迴圈」拉長成「30 分鐘自癒閉環」）／**Build for agents**（把 codebase 當成「每次都在重新入職的新員工」來準備環境）／Build a fast feedback loop（本地校驗＋property-based test）／Direction over execution（規格驅動）／**Treat code as disposable（程式碼可重寫，邊界測試才是契約）**／Hold the line on human standards／Trust the boundaries（防護欄工程）／Use agents for everything／Constantly tune your setup。
  - **AI Engineer 的 Harness Engineering Track**（World's Fair 2026）thesis 更狠：**「當 agent 在生產環境壞掉時，壞的很少是模型那一部分。」** 題目全是可抄的工程名詞：ports／proofs／kill switches、把任務與模型分離（DSPy）、Tokens Should Have Jobs（Anthropic）、Building the Production Cage for Domain Agents（AWS）、Agent Frameworks Considered Harmful、「我們讓 AI agent 執行 Bash 並活著回來講」（PostHog）。
  - 🏢 **這兩份合起來就是 P1–P4 的 retro 骨架，也是客戶提案的工程清單**（接 yt 那頁「Agent 上生產環境的安全與可靠性檢查表」，不必重寫）。
  - 🧠 對你個人最刺的一條是 **Maximize agent time**：你目前的 Vibe 節奏仍有大量「60 秒等待迴圈」——那正是把自己當人肉路由器。

### 單則精選

- **Codex 負責人 Tibo：harness 是拐杖，下一代模型會把它內化** — 🔁🧠 **這條修正我們上週要 ingest 的「harness＞模型」**：Tibo 說 harness 總是「走在模型前面」，Codex 團隊的工作本質是替模型搭拐杖（提醒跑測試、保持目標一致），**下一代訓練會把這些內化，拐杖就能拆，developer message 越來越短**——最新一代已不需要 `/goal` 就能專注跑一週的長任務。🏢 另外三個可直接用的點：①**安全審查已強制自動化，發現問題直接擋合併**（可抄進交付流程）②code review 的角色從「正確性檢查」轉向**「意圖討論」**（這件事不一定要圍繞程式碼發生）③**重構成本暴跌，所以好架構反而更重要**——「設計好盒子與不變量，盒子內部隨便改都不影響其他部分」。｜@宝玉 摘 The Pragmatic Engineer｜[原文](https://x.com/dotey/status/2098203738205024315) 🔗⚠️

- **Anthropic 官方降本三層：先別急著換便宜模型，先排除「為沒有價值的工作付費」** — 🔁🏢 官方把順序倒過來：多數團隊看到帳單上漲的第一反應（換模型／縮短輸入／少思考）**都可能直接傷到品質**。該先逐層檢查：**輸入層**＝重複內容被重新 prefill（查快取前綴、模型綁定、TTL）；**指令層**＝舊規則與新模型能力不再匹配（查**核驗儀式、強制步驟、陳舊樣例、衝突規則**）；**推理層**＝思考投入與任務難度不匹配（**用自己的 eval 掃過多個 Effort × 模型組合**，過高浪費、過低傷表現）。**這張表可以直接當「帳單健檢」的 SOP**，也是上週「規則刪除審計」的具體項目清單。｜@小互 摘 Anthropic 官方｜[導讀](https://x.com/xiaohu/status/2097664725873992054)｜[原文](https://best.xiaohu.ai/article/reducing-cost-improving-performance-claude-platform/) ⚡

- **宝玉的 code review 提示詞（三步，五分鐘可抄）** — 🧠⚡ ①先搞清楚這個 PR 要解決什麼問題 ②**如果不看這個 PR 的實作，你會怎麼實現？** ③review 程式碼後**對比你自己的方案**給出審查結果。妙處在第 2 步：逼 agent 先產生獨立判準，避免它只是順著既有實作點頭——**直接對治熱點卡 1 那個「agent review 變成複製貼上」的病**。｜@宝玉｜[原文](https://x.com/dotey/status/2097878840655626568) ⚡

- **兩個把 agent 拉回正軌的小技法：`Step back` ＋ sidechat** — 🧠⚡ ①agent 原地打轉時喊 **"Step back"**，讓它重看目標、檢查當前路徑是否有問題（宝玉說這也是他開會拉回主題的用詞）②讓它「跳出既有架構、基於目標重新設計」會給出不一樣的方案，但**必須用資料驗證**——他的做法是 **開一個 worktree 去跑對照**（結果：沒有預期那麼好，但可部分借鑑）③純粹要「解釋一下」的問題丟 **sidechat（`/btw`）**，不佔主上下文。**第 3 點正中你「不污染主 context」的偏好，第 2 點是 agent 版的最小驗證。**｜@宝玉｜[原文](https://x.com/dotey/status/2098945781885546788) ⚡🔗

- **Shopify 從 React Native 全面退回原生（Swift／Kotlin）——理由是 AI** — 🏢⚠️ 2020 年 All-in React Native 的旗手改口，原因不是 RN 變差，是 **coding agent 能拿著 iOS 版程式碼直接寫出 Android 版**，跨平台框架原本的價值主張（省人力、一次寫多端跑）被抵銷；靠共享規範、測試案例與 code review 維持兩端一致。Shop app **12 週**從 PoC 到重構完成上架。**→ 技術棧選型的邏輯被 AI 改寫了**：以往「為了省人力選跨平台」的預設，現在要重算；這同時是**給客戶的建議**與**我們自己接案報價**的變數。⚠️ 越出工具櫃邊緣（②前沿／④商業可續看），但對技術決策足夠具體，留在本櫃。｜@宝玉｜[中文整理](https://x.com/dotey/status/2098183477950603367)｜[Simon 的英文摘要](https://simonwillison.net/2026/Sep/10/shopify-react-native/) ⚠️
